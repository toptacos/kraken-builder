Why Kraken beats the alternatives

Posted under Internal Projects → Kraken. Benchmarks and examples on this page are produced by scripts in the repository and verified in CI.

Most plugin systems pick a language for you. Node for n8n. TypeScript inside the n8n process. Go providers for Terraform. JS actions for GitHub. Kraken picks the interface instead: one JSON object on stdin, one JSON object on stdout, exit 0. Everything below follows from that one decision.

1. It is the smallest thing that does the job

The core is 0.4 MB with exactly one dependency (pyyaml, MIT). The entire Homebrew install is 0.5 MB — we measured 33 MB once and cut it to that by shipping examples/tentacles without the 16 MB of vendored demo toolchains. No daemon. No server. No account. Run it on a Pi with the network unplugged; kraken demo still answers. 

$ curl -fsSL https://kraken.topta.co/install.sh | sh
$ kraken demo
{"v": 1, "id": "1", "ok": true, "result": {"arm": "geo", ...}}
// same contract, no SDK:
os.Stdin → json.Unmarshal → handle → os.Stdout → exit 0
process.stdin.on('end', () => {
  process.stdout.write(JSON.stringify({ v: 1, id: req.id, ok: true, result: {} }));
});

2. The contract is the integration surface

The same tentacle written six ways, all answering one command. This is not a slide — it is the verified output of docs/articles/polyglot.md: 

sh       {"lang": "sh", "id": "1", "ok": true}
python   {"lang": "python", "id": "1", "ok": true}
node     {"lang": "node", "id": "1", "ok": true}
php      {"lang": "php", "id": "1", "ok": true}
ruby     {"lang": "ruby", "id": "1", "ok": true}
perl     {"lang": "perl", "id": "1", "ok": true}
go       {"lang": "go", "id": "1", "ok": true}

One tentacle.yaml shape each. No lockfile, no plugin host, no rebuild. Rewrite the tentacle in another language tomorrow and the caller never notices.

3. Safe by default, off the network

Two guarantees, proven on this page's build machine, which had no internet:

  • Nothing calls home. An AST parse of core's imports finds urllib in exactly four modules — license, notify, network, sync — and every one of them is something a user opts into. A normal kraken run makes no outbound request.
  • Exposure is refused before it is granted. Ask the expose tentacle for a plan and you get a refusal that names the fix: {"ok": false, "result": {"error": "grant expose first: kraken grant expose"}}. After kraken grant expose, the same command returns a 127.0.0.1 bind with a note saying loopback only.

4. Composable without an event bus

A hook is just another tentacle. It returns a patch; core calls finish on the original tentacle with the raw result plus that patch. Verified end to end in docs/articles/hooks.md: 

$ kraken run stamper grow
{"v": 1, "id": "1", "ok": true, "result": {"arm": "stamper", "value": 3,
 "multiplier": 7, "saw_value": 3, "finished": true},
 "_hooks": [{"tentacle": "stamp", "ok": true, ...}], "finished": true}

Audit logs, notifications, cache warmers, post-processors — each is a tentacle you already know how to write, hanging off a run without touching its code.

5. And honest about where it loses

A binary tentacle costs one interpreter start, so a trivial kraken run is an order of magnitude slower than a C binary like make. Measured on one box, round-robin, min of N: kraken run 330 ms / 19 MB RSS, make ping 28 ms / 1 MB, node -e 87 ms / 30 MB.

What was in Kraken's control, we took: the CLI import chain went from 372.6 ms to 61.8 ms by making license, yaml, and the workflow thread pool load on first use instead of on --help, and one kraken run now parses its config chain once instead of four times. Method and before/after numbers: docs/BENCHMARKS.md.

So when is Kraken the wrong tool?

When the work is remote and long-lived: a 40-step CRM sync with OAuth refresh is n8n's job. Desired-state cloud infrastructure is Terraform's. Running one shell line is make's, and make will be faster. Kraken wins when the work is local, small, and you already trust the process — and it stays out of the way when it is not.
