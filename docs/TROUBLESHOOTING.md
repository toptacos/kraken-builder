# Troubleshooting

Every failure here is one a user hit and reported. The cause is named first,
then the fix, then the reason the fix is permanent.

## `ModuleNotFoundError: No module named 'kraken'`

The single most common report, and the one that looks least like an install
problem.

```
$ kraken
Traceback (most recent call last):
  File "/usr/local/bin/kraken", line 3, in <module>
    from kraken.core.cli import main
ModuleNotFoundError: No module named 'kraken'
```

Read that traceback literally and it says the package is not installed. It *is*
installed. Here is what actually happened on the machine this was written for:

```
$ pip show kraken-cli
Name: kraken-cli
Version: 0.1.1
Location: /usr/local/lib/python3.13/site-packages   ← dist-info, healthy
```

The `kraken` on PATH was a **pip console script** generated by
`pip install -e .`. Two absolute paths were frozen into it:

| Frozen path | Written where | After the repo moved |
|---|---|---|
| `#!/usr/local/opt/python@3.14/bin/python3.14` | the shebang | still exists on that one Mac, missing everywhere else |
| `…/Projects/Companies/TopTacos/Kraken/kraken-builder` | `__editable___kraken_cli_0_1_1_finder.py` | **gone** |

```python
# /usr/local/lib/python3.13/site-packages/__editable___kraken_cli_0_1_1_finder.py
MAPPING = {'kraken': '/Users/…/TopTacos/Kraken/kraken-builder/kraken'}
                        └── this directory no longer exists
```

The interpreter ran, trusted the `dist-info`, and asked the finder for
`kraken`. The finder pointed at a directory that had been moved to
`~/Projects/Kraken/kraken-builder`. Import failed. Nothing in the error mentions
a moved directory, a path, or the finder — which is why this reads as "not
installed" and sends people to reinstall something that is installed.

### Fix

```bash
python3 -m pip uninstall -y --break-system-packages kraken-cli   # macOS system python
```

`--break-system-packages` is needed only on a Homebrew or Debian python that
pip marks externally-managed (PEP 668). Drop it in a venv or with pipx.

That removes the console script from `/usr/local/bin`. Confirm what is left:

```bash
which -a kraken k
```

You want exactly one answer, or two pointing at the same file:

```
/Users/you/.local/bin/kraken
/Users/you/.local/bin/k
```

Then install the launcher:

```bash
sh ./install.sh
```

### Why it happened twice

The uninstall is necessary but not sufficient. `~/.local/bin/kraken` may be
**shadowed** by `/usr/local/bin/kraken`, because `/usr/local/bin` usually comes
first on `PATH`. `which -a kraken` prints the whole ordered list; the first
entry is the one that runs. On the machine above, three `/usr/local/bin/kraken`
entries preceded a perfectly good `~/.local/bin/kraken`.

## `kraken: cannot find the kraken source tree`

You moved the checkout and the launcher could not find it anywhere. The launcher
searches, in order:

1. `$KRAKEN_SRC`
2. `$HOME/.kraken/source` — written by `install.sh`
3. `$HOME/.kraken/src` — the default clone location
4. the repository containing the launcher script itself

Each candidate is checked for `kraken/core/cli.py` before use, so a stale entry
is skipped rather than trusted.

```bash
export KRAKEN_SRC="$HOME/Projects/Kraken/kraken-builder"
```

To make it permanent, re-run the installer from the new location:

```bash
KRAKEN_SRC="$HOME/Projects/Kraken/kraken-builder" sh ./install.sh
```

That rewrites `$HOME/.kraken/source`.

## `kraken doctor`

```
kraken doctor
```

Prints JSON and exits `2` when any check fails. The `install.*` checks answer
the question the traceback never did: *which copy of kraken is running, and
what else is competing for the name?*

| Check | Fails when | Means |
|---|---|---|
| `install.source` | `kraken/core/cli.py` is missing from the running tree | a partial or wrong checkout |
| `install.revision` | never fails | commit and dirty state; "packaged install" for brew/pip |
| `install.pip_kraken_cli` | a `kraken_cli-*.dist-info` is on `sys.path` | **the failure above** — a competing console script exists |
| `install.pointer` | never fails | `$HOME/.kraken/source` vs the tree that actually ran; says `stale` if they differ |
| `install.on_path` | `kraken` is not on PATH at all | run `install.sh` |

The other checks — `layout.*`, `protocol`, `catalog`, `plan.*`, `licenses.*` —
are unchanged.

## Two copies of the repo

The most expensive mistake, because it is silent. A clone at `~/.kraken/src`
for the launcher, and a working checkout at `~/Projects/Kraken/kraken-builder`
for editing. You edit one and run the other.

```bash
kraken doctor | grep install.source
```

If that path is not the directory you have open, you are editing the wrong tree.
Delete the extra clone, or point `KRAKEN_SRC` at the one you actually work in.

## A dangling `.git` file

```
$ cd kraken-builder && git status
fatal: not a git repository: …/.git/modules/Kraken/kraken-builder
```

`kraken-builder/.git` is a *file*, not a directory, containing
`gitdir: ../../.git/modules/Kraken/kraken-builder`. That gitdir does not exist —
usually the residue of a repo that was converted to a submodule and then moved
out of, or a clone copied without its gitdir.

History is not lost if a parent repository tracks the files as ordinary paths:

```bash
cd .. && git log --oneline -- kraken-builder
```

If that prints commits, the files are safe. Move the dangling pointer aside and
carry on as a plain subdirectory:

```bash
mv .git .git.dangling
```

If it prints nothing, do **not** delete anything — recover the gitdir from a
backup first.

## Design rules this page exists to enforce

**Rule 1 — never bake an absolute path into anything a user runs.** The
launcher resolves its source tree on every invocation. `install.sh` writes
`$HOME/.kraken/source` so a move is a one-line repair instead of a reinstall.

**Rule 2 — prefer a launcher over `pip install -e .` for a dev checkout.** An
editable install is a claim that this machine's path layout is permanent. It is
not. `pip install -e .` is fine inside a throwaway venv; it is wrong as the way
you install a tool you work on.

**Rule 3 — one entry point per name.** If `kraken` resolves to more than one
file, you do not know which one ran. `which -a kraken` after any install.

**Rule 4 — check the exit code, not the presence of a command.**
`command -v kraken` succeeds when the file is broken. `kraken self plan` is the
honest test.

## Still stuck

Include the output of these three, which between them identify every variable
above:

```bash
which -a kraken k
cat ~/.kraken/source 2>/dev/null
kraken doctor
```

Then [open an issue](https://github.com/toptacos/kraken-builder/issues). Never
paste `~/.kraken/keys`.
